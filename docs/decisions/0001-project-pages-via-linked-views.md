# 프로젝트별 표시는 DB를 나누지 않고 링크드 뷰로 한다

| | |
|---|---|
| **ID** | ADR-0001 |
| **Date** | 2026-08-14 |
| **Status** | Accepted |
| **관련 작업 항목** | `docs/02-design/features/records-and-work-items.design.md` (기록/작업항목 2계층 설계) |
| **결정자** | Sol |

## 1. 배경

Notion 업무일지에서 프로젝트별로 보기가 불편하다는 문제에서 출발했다. 처음에는
"속성이 28개라 너무 많다"로 진단했으나, **측정해 보니 사실이 아니었다.**

2026 DB의 실제 상태 (`list_views`, `query_database_rows`로 조회):

```
행                566
속성               28
뷰                 11   Default view 15컬럼 / 도구 생성 뷰 4~9컬럼
프로젝트           17
```

어느 뷰도 28컬럼을 보여주지 않는다. 제일 넓은 것이 처음 열리는 `Default view`의
15컬럼이다. 남은 진짜 불편은 **한 프로젝트만 담긴 화면이 없다**는 것이다.
`프로젝트별` 뷰가 있으나 필터가 없어 17개 프로젝트가 한 표에 함께 있다.

속성이 실제로 안 쓰이는지도 확인했다. 현재 계약으로 쓰인 63행 기준:

```
100% 채워짐        Name Date Project Categories Session ID Purpose Branch
                  Status Work Period Task Group Review Status Schema Version
0%                Parent Task, Sub-items   (legacy, 네이티브 관계쌍으로 대체)
```

`Task Group`은 옛 행에서 2.4%였으나 현재 계약에서는 100%다. **옛 행의 빈 칸은
"안 쓰는 칸"이 아니라 "그때 없던 칸"이었다.** 따라서 스키마를 줄일 근거는
legacy 관계쌍 2개 외에는 측정되지 않았다.

## 2. 선택지

| | A. 프로젝트별 DB로 분할 | B. 프로젝트 페이지 + 링크드 뷰 | C. 뷰 컬럼만 정리 |
|---|---|---|---|
| DB 개수 (2026) | 17 | 1 | 1 |
| `ensure`가 조정할 대상 | 17 DB | 1 DB | 1 DB |
| `ensure`가 만들 뷰 | 10 × 17 = 170 | 10 | 10 |
| `ops` | 17개 조회 후 합산 | 그대로 | 그대로 |
| 캐시 모델 | `year+project → db_id`로 변경 | `year → db_id` 유지 | 유지 |
| 프로젝트 전용 화면 | 있음 | 있음 | **없음** |
| 저장소 이름 변경 시 | **행 이동 필요** | 필터 값 수정 | 필터 값 수정 |

## 3. 결정

**연도당 DB 하나를 유지하고, 프로젝트별 화면은 그 DB를 가리키는 필터된 링크드
뷰를 프로젝트 페이지에 얹어서 만든다.**

## 4. 근거

### A(프로젝트별 DB)를 버린 이유

**스키마 조정 코드의 접촉면이 17배가 된다.** 이 프로젝트에서 데이터를 잃은
유일한 사건이 그 코드에서 났다 — `docs/postmortem/2026-08-07-ensure-wipe.md`,
`ensure`의 PATCH 한 번이 **497행에서 속성 6개를 비웠고 복구하지 못했다.**
그 코드가 닿는 DB를 1개에서 17개로 늘리는 것은, 얻는 것에 비해 감당할 수 없다.

**저장소 이름이 바뀌면 되돌릴 수 없다.** 지금 DB에 `claude-code-hooks-diary`
50행과 `working-diary` 45행이 따로 있는데 **같은 저장소다**(루트에
`claude-code-hooks-diary.iml`이 남아 있다). 한 DB에서는 select 값 하나를 고치면
95행이 합쳐진다. DB가 나뉘어 있으면 50행을 옮겨야 한다.

**연도→DB가 1:1이라는 모델을 깨야 한다.** `notion_cache.get_database(cache,
year)`가 연도당 하나만 돌려주고, `ensure_database(year)` 호출부가
`notion_push`·`notion_ensure`·`notion_ops`·`ordinals`·`relations`에 흩어져 있다.
프로젝트 축을 넣으려면 이 전부를 바꿔야 하는데, 이번 결정이 풀려는 문제보다 큰
변경이다.

**프로젝트 17개 중 6개가 9행 이하다.** 1행짜리도 있다. 그것들에 각각 DB와 뷰
10개를 만드는 것은 비용만 있고 이득이 없다.

### C(뷰 컬럼만 정리)를 버린 이유

가장 싸지만 **원하는 것을 주지 않는다.** 컬럼을 줄여도 17개 프로젝트가 한 표에
섞여 있는 것은 그대로다. 다만 이 안의 내용(넓은 뷰 정리)은 B와 배타적이지
않으므로 함께 한다.

### B를 고른 이유

프로젝트 전용 화면이라는 이득을 가져가면서 위험한 코드에 손대지 않는다.
Notion의 링크드 뷰는 원본 DB를 그대로 따라가므로 데이터가 두 벌이 되지 않는다.

## 5. 영향 범위

| 대상 | 영향 |
|---|---|
| 스키마 | **없음.** 속성 28개 그대로 |
| `ensure` | **없음.** 계속 연도 DB 하나만 조정 |
| 캐시 | **없음.** `year → db_id` 유지 |
| `ops`/`push`/`report` | **없음.** 모두 연도 DB 하나를 본다 |
| Notion 워크스페이스 | 연도 페이지 아래 프로젝트 페이지가 생기고, 각 페이지에 필터된 링크드 뷰가 얹힌다 |
| 기존 566행 | **손대지 않는다** |

## 6. 검증 방법

- 프로젝트 페이지에서 그 프로젝트 행만 보이고, 다른 프로젝트 행이 새로 들어와도
  섞이지 않는지 확인한다
- 링크드 뷰에서 값을 고치면 원본 DB에 반영되는지 확인한다 (링크드 뷰는 사본이
  아니어야 한다)
- `agent-diary diary-notion push` 후 새 행이 해당 프로젝트 페이지에 자동으로
  나타나는지 확인한다 (필터가 `Project`에 걸려 있으므로 나타나야 한다)
- `agent-diary diary-notion ensure`를 돌린 뒤에도 프로젝트 페이지의 링크드 뷰가
  남아 있는지 확인한다 — `ensure`가 DB의 뷰만 조정하고 다른 페이지의 뷰는 건드리지
  않아야 한다

## 7. 되돌릴 조건

- 한 프로젝트의 행이 **연 1,000행을 넘어** 링크드 뷰의 응답이 실사용에 지장을 줄 때
- 프로젝트마다 **서로 다른 속성**이 필요해져 한 스키마로 감당되지 않을 때
- 특정 프로젝트만 외부에 공유해야 하는데 링크드 뷰로는 원본 DB 접근 권한이 함께
  넘어가서 곤란할 때

셋 다 지금은 해당되지 않는다. 가장 큰 프로젝트가 239행이고, 속성은 모든
프로젝트가 같은 것을 쓰며, 공유 요구는 아직 없다.

## 8. 미해결

- **링크드 뷰를 API로 만들 수 있는지 확인되지 않았다.** 현재 `create_view`
  페이로드는 `database_id`와 `data_source_id`만 갖고 **부모 페이지 필드가 없다**
  (`notion_views.py:588` `_payload_for_spec`). 2025-09-03 API가 뷰의 부모를
  받는지는 코드로 알 수 없다. 따라서 프로젝트 페이지 구성이 **도구 자동화**인지
  **Notion UI에서 1회 수동 설정**인지 정해지지 않았다. 수동은 확실히 가능하다
- `Default view`가 15컬럼으로 가장 넓고 처음 열린다. 줄일지 여부는 이 결정과
  별개이며 위험이 없다
- **`Project`와 `Repository` 분리는 이 결정에 포함되지 않았다.** 별도 결정으로
  다룬다. 다만 위 이름 변경 사례(`claude-code-hooks-diary` → `working-diary`,
  GitHub은 내내 `agent-diary`)가 그 안건의 근거가 된다
- 기록/작업항목 2계층 설계의 열린 질문 6가지는 그대로 남아 있다. 이 결정은 그중
  어느 것도 정하지 않으며, DB를 나누지 않기로 한 것만으로 2계층 설계의 전제
  ("두 번째 DB가 아니라 같은 DB의 부모 행")와 어긋나지 않는다
