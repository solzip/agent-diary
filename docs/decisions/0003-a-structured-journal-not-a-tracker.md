# 이 데이터베이스는 구조를 가진 일지다. 상태를 관리하지 않는다

| | |
|---|---|
| **ID** | ADR-0003 |
| **Date** | 2026-08-14 |
| **Status** | Accepted |
| **관계** | [ADR-0002](0002-two-layer-records-and-work-items.md)의 "작업항목은 상태를 갖는다"를 대체한다. 2계층 자체와 세션 넘는 연결 검증은 그대로 유효하다 |
| **결정자** | Sol |

## 1. 배경

이 도구는 일지다 — Stop Hook이 세션마다 무슨 일이 있었는지 자동으로 적는다.
그런데 Notion 쪽 스키마에는 수명주기를 가진 것에만 의미가 있는 필드가 붙어 있다:
`Status`, `Priority`, `Blocked`, `Review Status`, `Carryover`, `Next Action`.

**둘이 섞여 있는지 확인하기 위해 사람이 그 필드를 움직인 적이 있는지 쟀다.**

```
Review Status
   Needs Review    266
   (비어있음)       300
   Reviewed          0     <- 566행 중 한 번도 없음

Blocked 켜진 행                  9   (1.6%)
생성 후 한 번도 수정 안 된 행    89%
생성 1시간 뒤에도 수정된 행      52   (9.2%)
```

`diary-notion review --apply`는 만들어져 있고, **한 행도 `Reviewed`로 옮긴 적이
없다.** 상태 필드는 push 시점에 에이전트가 써넣고 그대로 굳는다.

그 결과가 이미 관측된 증상들이다. 완료율 6%는 기록이 완료될 수 없기 때문이고,
`Testing` 53%·중앙값 44일은 체류 시간이 아니라 **그 세션이 끝났을 때의 상태**다.
2026-08-14에는 실제 배포가 네 번(v4.11.0~v4.11.3)인데 **10개 행이 `Deployed`로
찍혔다.**

반면 Sol이 실제로 원한다고 말한 것은 상태 추적이 아니었다.

> 기능 1개에 속한 구현 목록 10개를 기록하고 그 하위 동작들을 엮어서 기록하고 싶다

그리고 그 계층은 이미 동작한다. 같은 날 올린 11행이 Notion에서 이렇게 들어갔다:

```
프로젝트 전수 검사
    └ 공개 저장소 소스의 실명·홈 경로 제거
    └ sdist 자가 테스트 복구와 침묵 핸들러 4곳
    └ 중복 상수 단일화와 미사용 상수 3개 제거
```

## 2. 선택지

| | A. 일지 전용 + 계층 | B. 2계층 상태 관리 | C. 지금처럼 |
|---|---|---|---|
| 상태 필드 | 없음 | 작업항목에 있음 | 기록마다 있음 |
| 필요한 것 | 계층 (이미 됨) | **사람이 상태를 유지해야 함** | 없음 |
| 완료율·stale 집계 | 묻지 않는다 | 작업항목 기준 | 6%가 계속 나온다 |
| `Reviewed` 0회가 말하는 것 | 이 안과 일치 | **전제에 대한 반증** | — |

## 3. 결정

**A.** 이 데이터베이스는 무슨 일이 있었는지를 **구조를 갖춰** 기록한다. 상태를
관리하지 않는다. 계층은 진행 상황을 추적하기 위한 것이 아니라 **기록을 엮기 위한
것**이다.

배포는 예외다. 배포는 상태가 아니라 **일어난 사건**이므로 기록에 남는다. 다만
**"함께 나간 단위"에만** 붙는다.

## 4. 근거

### B를 버린 이유

B는 "Sol이 작업항목의 상태를 유지한다"를 전제한다. **566행에서 `Reviewed`가 0회**인
것이 그 전제에 대한 직접적인 반증이다. 행 수가 줄면 가능해질 수도 있지만, 그것은
희망이지 근거가 아니다. 유지되지 않을 상태 필드는 비어 있는 것보다 나쁘다 — 굳어
있는 값이 현재 상태처럼 읽히고, 그것을 집계한 6%가 계속 나온다.

관측 하나 더: 2026-08-14 하루 동안 "남은 일이 무엇인가"를 물을 때마다 실제로 읽은
것은 Notion이 아니라 `docs/plans/next-session.md`였고, Sol이 "정본은
next-session.md"라고 직접 말했다. **PM 표면은 이미 저장소 안에 있다.** (이 세션에서의
관찰이며 장기 통계는 아니다.)

### 배포를 남기는 이유와 그 단위

배포는 밀릴 수 있다는 지적이 있었다. 해법은 필드가 아니라 규칙이다 — **일어난 것만
적는다.** 비어 있으면 아직 안 나간 것이고, 예정일은 적지 않는다. 예정을 적지 않으면
밀림이 필드를 오염시킬 수 없다.

"구현 10개 모두에 배포를 적나"에 대한 답은 계층이 이미 준다:

```
프로젝트 전수 검사           <- v4.11.0  (셋이 함께 나갔다)
    └ 실명 제거
    └ sdist 복구
    └ 상수 단일화

한글 콘솔 출력 실패          <- v4.11.1
    └ 폴백을 ASCII로          <- v4.11.2  (따로 나갔으므로 자기 것을 가진다)
```

**따로 나갔으면 각자, 함께 나갔으면 위가 갖는다.** 계층이 그 단위를 이미 표현하므로
별도 규칙이 필요 없다.

## 5. 영향 범위

| 대상 | 영향 |
|---|---|
| 스키마 | `Status` `Priority` `Blocked` `Block Reason` `Review Status` `Carryover` 제거 대상 (26 → 20). 배포 표시 필드 1개 추가 |
| `ops` | 완료율·stale·needs review 계산이 근거를 잃는다. **제거하거나 의미를 다시 정의해야 한다** |
| 뷰 | `Blocked`, `전날 미완료`, `리뷰 필요`가 근거를 잃는다 |
| 스킬 계약 | 태스크마다 status/priority를 정하라는 지시를 뺀다 |
| `diary-notion review` | 명령 자체의 존재 이유가 사라진다 |
| 기존 566행 | 값은 남는다. 읽지 않을 뿐 |

**이 목록이 이 결정의 진짜 비용이다.** 필드 여섯 개가 아니라 그것을 읽는 명령과
뷰가 함께 정리되어야 한다.

## 6. 검증 방법

- `ops`가 "완료율"이라는 단어를 쓰지 않는지
- 배포 표시가 **따로 나간 것에만** 붙는지 — 한 릴리스에 여러 행이 표시되면 규칙이
  지켜지지 않은 것
- 계층이 세션을 넘어서 이어지는지 (ADR-0002의 조회 구현 이후)

## 7. 되돌릴 조건

- Sol이 Notion에서 상태를 보고 실제로 판단을 내리는 일이 생길 때. 그때는 B가 맞다
- `next-session.md`가 감당 못 할 만큼 미결 항목이 늘어 Notion으로 옮겨야 할 때

## 8. 미해결

- **배포 표시의 형태.** 체크박스 / 날짜 / 릴리스 식별자(`v4.11.3`). 이 저장소는
  태그로 배포하므로 식별자가 셋 다 답하지만, `erp_chatbot_solzip`처럼 태그가
  없을 수 있는 프로젝트가 어떻게 배포되는지 확인되지 않았다
- **세션 넘는 부모 조회의 키.** ADR-0002의 미해결 그대로. 계층이 세션을 넘으려면
  필요하다
- **연말 경계.** DB가 연도별인데 해를 넘기는 계층의 자리
- **깊이.** 지금 2단계까지 실제로 쓰였다. "구현 → 하위 동작" 3단계가 필요한지 미확인
- **상태 필드 제거의 순서.** 필드를 지우기 전에 `ops`와 뷰를 먼저 정리해야 한다.
  순서가 반대면 읽는 쪽이 조용히 빈 값을 받는다
