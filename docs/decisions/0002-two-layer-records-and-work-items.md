## 1. 배경

설계 문서는 2계층(상태를 갖는 작업항목 + 상태가 없는 기록)을 제안하면서, **그
전제가 검증되지 않았다는 것을 스스로 적어놓았다.**

> `parent_progress`는 돌지만, 이 설계가 존재하는 이유인 바로 그 경우에는 한 번도
> 돈 적이 없다. "보고하는 절반은 이미 있다"는 과장이다.

이유는 구조적이었다. `_wire_parent_tasks`는 이번 push가 만든 행들(`row_ids`)
안에서만 인덱스를 짝지으므로, **이전 세션의 행을 부모로 삼는 경로가 아예 실행될 수
없었다.** 그래서 데이터베이스의 계층 링크 82개가 전부 세션 내부였고, 세션을 넘는
연결이 Notion에서 되는지, 집계가 그것을 읽는지 아무도 몰랐다.

설계 문서의 착수 순서 3번이 이것이었다 — "행 하나를 손으로 연결해보고 읽어본다.
기능이 아니다. 이것이 나머지를 시작할 가치가 있는지 결정한다."

## 2. 선택지

| | A. 2계층으로 간다 | B. 기록 한 층으로 남는다 |
|---|---|---|
| 상태를 어디에 두나 | 작업항목 행 | 기록마다 (지금) |
| 89%가 수정되지 않는 행에 상태 필드 | 없음 | 그대로 |
| 완료율의 의미 | 작업항목 기준 | **기록은 완료될 수 없으므로 6%가 계속 나온다** |
| 구현 필요 | 이전 세션의 부모를 찾는 조회 | 없음 |
| 전제 | 세션 넘는 연결이 되어야 함 | 없음 |

B는 아무것도 안 하는 안이지만 진짜 선택지다 — 전제가 깨졌다면 이쪽으로 가야 했다.

## 3. 결정

**2계층으로 간다.** 전제가 실측으로 확인되었다.

## 4. 근거

2026-08-14, 라이브 데이터베이스에서 실험했다. 서로 다른 세션에서 만들어진 실제
행 두 개를 골랐다:

```
자식  63차 IF-67 TurnPlan 디스패치 복구 (2차)
      세션 session_01PhRdzHKMScdUmyU4apZsJS
부모  62차 IF-68 confidence 섀도 및 OP-11 마스킹 해소
      세션 b2b01608-27a7-4575-ba1b-cddc4421bc90
```

도구 자신의 메서드(`update_row_native_parent`)로 연결하고 읽어본 결과:

| 확인 항목 | 결과 |
|---|---|
| Notion이 세션 넘는 링크를 받는가 | 예 |
| 반대편이 자동 동기화되는가 | 예 (`상위 항목` ↔ `하위 항목`) |
| `ops`의 `parent_progress`가 읽는가 | 예 — `children: 1, active: 1, done: 0` |

즉 **막혀 있던 것은 플랫폼이 아니라 구현이다.** Notion도 도구의 쓰기 경로도 집계도
전부 동작하며, 없는 것은 "이전 세션의 부모 행을 찾는 조회"뿐이다.

실험 링크는 원상복구했다. 자식과 부모 양쪽 관계가 비어 있는 것을 확인했다 — 63차가
62차의 하위라는 관계는 실험을 위해 임의로 만든 것이고 사실이 아니다.

### B를 버린 이유

전제가 확인된 이상 B는 "완료율 6%를 영구히 받아들인다"는 뜻이 된다. 기록은 완료될
수 없는데 완료 여부를 묻는 집계가 계속 나오고, 그것을 읽는 사람은 계속 잘못된
결론을 얻는다.

## 5. 영향 범위

| 대상 | 영향 |
|---|---|
| 스키마 | 작업항목 행이 생긴다. 속성 추가는 아직 없음 |
| `_wire_parent_tasks` | **이전 세션의 부모를 찾는 조회가 필요하다** — 이 결정이 만드는 유일한 필수 구현 |
| `ops` | `parent_progress`는 이미 동작한다. 완료율의 분모가 작업항목으로 바뀐다 |
| 기존 566행 | 손대지 않는다. 소급 연결은 별도 |
| 뷰 | 기록과 작업항목이 한 DB에 섞이므로 뷰가 어느 쪽인지 말해야 한다 (ADR-0001에서 받아들인 비용) |

## 6. 검증 방법

- 서로 다른 세션에서 만들어진 행을 도구가 **자동으로** 부모에 연결하는지 (지금은
  손으로만 됨)
- `ops`의 완료율이 기록이 아니라 작업항목 기준으로 계산되는지
- 부모를 못 찾았을 때 조용히 건너뛰지 않고 보고하는지

## 7. 되돌릴 조건

- 이전 세션의 부모를 찾는 조회가 **틀린 부모에 붙이는 사례**가 관측될 때. 잘못된
  계층은 없는 계층보다 나쁘다
- 작업항목 행이 기록보다 빠르게 늘어날 때 — 그러면 2계층이 아니라 이름만 다른
  1계층이다

## 8. 미해결

이 결정은 "2계층으로 간다"만 정한다. 다음 네 가지는 각각 따로 정한다.

- **배포 구분** — 상태값 / 별도 체크박스 / 범위 밖
- **연결 안 된 기록** — 암묵적 1행 작업항목 / 떠 있는 채로
- **식별자 방식** — 제목에서 제안 vs `Task Group` 직접 작성. **이전 세션의 부모를
  찾는 조회 키가 곧 이것이므로, 5번 구현이 이 결정에 달려 있다**
- **연말 경계** — DB가 연도별인데 해를 넘기는 작업항목. `Task Group`이 select인
  한 옵션이 DB마다 따로라 구조적으로 풀리지 않는다

그리고 관측 하나: `Task Group` 25개 중 **세션을 넘는 것은 1개뿐**이다
(`chatbot-verification-track`, 12행 2세션). 나머지 24개는 단일 세션이고 그중 10개는
한 행짜리다. 세션을 넘으라고 만든 필드가 실제로 넘은 적이 거의 없다.
